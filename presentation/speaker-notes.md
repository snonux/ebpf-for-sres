## Section: basics

_What BPF is, the VM, the verifier and where programs attach_

### 2. "What is this process doing right now, and why is it slow?"

`why-bpf` · 2:00 min · starts at 0:30

Start with the question every on-call engineer asks. Most of us reach for iostat, vmstat and top first, and we should: they are cheap and installed everywhere. But they read counters and print averages for the whole box or the whole device. They tell you that the disk is slow or the run queue is long, not which process, file or request, and an average hides exactly the outliers that cause timeouts. strace does show individual syscalls, but through ptrace, which stops the target on every syscall and can slow it down many times over: careful on a busy production process. perf is great for busy on CPU, weaker for waiting on something. BPF answers the follow-up question at the event level, with distributions instead of averages and without restarting anything, which is why each row has a BPF counterpart, several of them in today's examples.

### 3. Small programs the kernel runs when something happens

`what` · 1:30 min · starts at 2:30

What it is, and the name in one go. Think of it as JavaScript for the kernel: instead of patching the kernel, loading a module or rebooting, you attach a small sandboxed program to an event. Three properties matter: it is event-driven, the verifier makes it safe, and the JIT makes it fast. That combination is what makes it usable on production machines. On the name: BPF was invented at Berkeley Lab in 1992 to filter packets cheaply, and tcpdump still compiles its filters to classic BPF. In 2014 Alexei Starovoitov's extended BPF landed in Linux 3.18 and turned it into a general-purpose in-kernel VM. Nobody writes classic BPF any more, so BPF and eBPF mean the same thing today, and the instruction set is now an IETF standard. Windows has a port in progress with different hooks, so everything in this talk is Linux, and the examples target Rocky Linux 9.9.

### 4. A small virtual machine inside the kernel

`vm` · 1:30 min · starts at 4:00

This is where the program actually lives. The loader in user space hands bytecode to the kernel with the bpf() syscall. Inside the kernel it lands in a small virtual machine, a sandbox. The verifier checks the program first; only then does the JIT turn it into native machine code. The next slides look at the verifier and the hooks in turn. Hooks such as uprobes in your app, kprobes, tracepoints, network and scheduler events trigger it. The program can only touch the outside world in two ways: helpers, a fixed list of kernel functions it is allowed to call, and maps, memory it shares with user space. Maps hold totals and state, like counters and histograms; a ring buffer map streams one record per event, which is how you share content such as file names or request details rather than just numbers. Global variables go the other way: user space sets them, for example a PID to filter on, and the program reads them. Your tool reads maps with the same bpf() syscall and the ring buffer through mmap, so events are not copied. That sandbox is why you can run this on production hosts. Think of it in two phases: once, at load time, compile, load, verify, JIT and attach; then every time the event fires, the program runs, writes into a map or the ring buffer, and your tool reads it.

### 5. C or Rust in the kernel, any language in user space

`languages` · 0:30 min · starts at 5:30

Whatever you write, it ends up as the same BPF bytecode. On the kernel side that is C with a lot of restrictions, which is why people call it pseudo C: no standard library, a tiny stack, no unbounded loops, and the verifier has to be able to prove every memory access is safe. The one real alternative for the kernel side is Rust, through Aya, which compiles Rust to BPF with its own linker. GCC can also compile C to BPF, next to clang. bpftrace has its own little language and generates the bytecode for you. Go is not a kernel-side option: there is no Go-to-BPF compiler, so libbpfgo and cilium/ebpf load a program written in C and compiled with clang; cilium/ebpf can also assemble raw BPF instructions from Go, but nobody writes real tools that way. On the user side any language that can make the bpf() syscall works; libbpf in C is the reference, and libbpfgo wraps it for Go, which is what ior and our examples use.

### 6. What the kernel checks, and what it cannot

`verifier` · 1:00 min · starts at 6:00

The verifier is what makes BPF safe enough for production, so it is worth knowing what it does. It simulates the program on every path, which is why loops must be bounded and why big programs fail with a complexity error. It checks every memory access and forces you to handle a failed map lookup. What it proves is that your program cannot crash the kernel or hang it. It does not stop a correct program from being expensive: attaching to a very hot event, allocating a map with millions of entries, or making all CPUs fight over one lock or one shared counter is all allowed. Those are the ways BPF tools hurt production boxes in practice.

### 7. Small on purpose, and growing with every kernel

`limits` · 1:00 min · starts at 7:00

The sandbox is small on purpose, and it is worth knowing the numbers, because hitting them is the most common surprise. Program size: originally 4096 instructions. Since kernel 5.2 there is no fixed size; instead the verifier analyses up to one million instructions across all paths and then rejects the program as too complex. Loops: none at first, bounded loops since 5.3, and a bpf_loop helper since 5.17 for longer ones. The stack is 512 bytes, which is why larger buffers live in maps; the newest kernels allow up to 2 KiB on x86-64 and arm64. Function calls can nest 8 deep and tail calls chain 33 times. For sending events to user space, the ring buffer arrived in 5.8: you choose its size, a power of two, and when it is full events are dropped, never the traced process blocked. Without root, the old 4096-instruction limit still applies. The trend is clear: every kernel generation raises the limits. On Rocky 9 the 5.14 kernel has everything up to 5.14, and Red Hat backports newer features, so test rather than assume. The practical rule stays the same: keep the kernel half small, filter and count there, and do everything else in user space.

### 8. The only kernel functions a program may call

`helpers` · 1:00 min · starts at 8:00

A BPF program cannot call arbitrary kernel functions. It can only call helpers, a fixed list the kernel exposes, and each program type gets its own subset. On the left are the ones our examples use, and they only observe: who is running, its name, a timestamp for latencies, our own maps, a safe copy of a string such as a file name, and the ring buffer to send an event to user space. BPF_CORE_READ, which we meet later, is in the same family. But BPF is not read-only by nature. Networking programs rewrite and redirect packets; that is how load balancers and Cilium work. bpf_override_return makes a kernel function return an error without running it, for fault injection, and only on functions the kernel marks as safe for that. bpf_probe_write_user writes into a process's memory; the man page itself warns of a risk of crashing the system and running programs, and the kernel logs a warning when such a program is attached. A program can never write arbitrary kernel memory, but with these helpers a verified program can still break a service: drop the wrong packets, fail the wrong call. So keep the two worlds apart in your head. Everything in this talk observes only: it reads, counts and reports, and that is why it is comfortable to run on production.

### 9. Where you can attach a program

`hooks` · 0:45 min · starts at 9:00

For observability the top row matters most. Tracepoints are a stable interface the kernel promises to keep; kprobes can hook nearly any kernel function but may break across kernel versions. uprobes do the same for user-space code. The bottom row shows eBPF is not only for tracing: Cilium, Katran and others run networking and security in eBPF too. Today we use the top row: tracepoints in most examples, a kprobe in example 06, a uprobe in example 07. The next two slides take the kernel hooks and the user-space hooks in turn.

### 10. Tracepoints first, then the rest

`tracepoints` · 1:30 min · starts at 9:45

Tracepoints first. A tracepoint is a call that kernel developers placed in the code on purpose, like trace_block_rq_issue when a block request goes to the device. Its name and arguments are a promise not to change lightly, and when nobody is attached the call is patched out and costs essentially nothing. There are a few thousand: every syscall, the scheduler, block, network, the file systems. If they cover your question, use them. If not, go down the ladder. First look for a nearby tracepoint. Second, fentry and fexit: the entry or return of any kernel function that is not inlined, cheap, and it works on Rocky 9. Third, the classic kprobe and kretprobe on the same functions. Fourth, a kprobe at an offset inside a function, precise but valid for one kernel build only. The further down, the more your tool depends on kernel internals. bpftrace -l lists all of them.

### 11. uprobes and USDT: tracing your own code

`uprobes` · 1:00 min · starts at 11:15

Everything so far was the kernel. uprobes do the same for user space: put a probe on any function in a binary or shared library, with no code change and no restart. For compiled languages, C, C++, Rust and Go, that works on any function symbol, as long as the binary is not stripped. One trap with Go: do not use uretprobes. The return probe rewrites the return address on the stack, and when Go grows and moves a goroutine stack the runtime finds that address and kills the process with unknown caller pc; the Go issue for it has been open since 2017. Put uprobes on the function's RET instructions instead. Shared libraries are the sweet spot: one probe on getaddrinfo in libc covers every program, that is example 07, and a probe on SSL_write in OpenSSL shows data before it is encrypted. For JIT-compiled and interpreted languages a uprobe has nothing stable to attach to, because the code is generated at run time. So the runtimes ship USDT probes, static markers compiled in, the same ones DTrace uses. HotSpot has probes for GC, class loading, threads and compilation; method entry and object allocation need -XX:+ExtendedDTraceProbes and are slow. CPython has function entry and return and GC markers if it was built with --with-dtrace; check with readelf -n for stapsdt notes. bpftrace -l lists what a binary offers. Remember the cost: each uprobe hit is a trap into the kernel, microseconds, so not on malloc.

### 12. bpftrace: one line, one question

`try` · 1:30 min · starts at 12:15

bpftrace is awk for kernel events, and this one slide is all the bpftrace syntax we need today. Every program is a probe, an optional filter and an action. ### 14. bpftrace compiles on the host you are debugging

`bpftrace-inside` · 1:30 min · starts at 15:45

bpftrace is the easy part, and here is the catch that shapes the rest of the talk. bpftrace is a complete compiler: it parses the script, resolves types from the running kernel, and then LLVM compiles it to BPF, on the host you are tracing, every time you start a script. You just saw that scroll by with -d all. Three consequences. First, every host needs the toolchain: in our sandbox bpftrace pulls in about 160 MB of LLVM and Clang libraries. Second, speed: in an incident you do not want to start by installing packages and compiling on the box that is in trouble, and in a distroless container you cannot. Third, security: a compiler on a production host is more to patch and a gift to an attacker, and many hardening baselines forbid it. bpftrace stays the right tool for exploring on a box where it is already installed. But for anything you want ready before the incident, we want a binary that is built and tested ahead of time and simply runs everywhere. The next slides are about what stands in the way of that, and how CO-RE removes it.

## Section: portable

_Build once: kernel differences, BTF, CO-RE, and static Go binaries with libbpfgo_

### 15. Every host runs a different kernel

`kernel-versions` · 1:00 min · starts at 17:15

If we compile ahead of time, the binary meets kernels we have never seen. Three things differ. Function names change, so kprobes fail to attach; tracepoints are the stable answer, which is why our tools use them. Struct layouts change, so a hard-coded offset reads garbage. A real example we hit with ior and in these examples: RHEL 9 backports a patch that makes the BTF type trace_event_raw_sys_enter 8 bytes wider than what a syscall tracepoint program really gets, so the verifier rejects such programs with EACCES on stock Rocky 9; every example here uses struct syscall_trace_enter instead. And features arrive over time, but Red Hat backports a lot into 5.14, so probe for features rather than comparing version numbers. Compiling on each host, as bpftrace does, sidesteps the struct problem. To build once we need another answer for it, and that is CO-RE.

### 16. BTF: the kernel describes its own types

`btf` · 1:15 min · starts at 18:15

To build once and run everywhere we need one more ingredient: the kernel has to tell us where things are. That is BTF, the BPF Type Format: a compact description of every type in the running kernel, every struct and every field with its offset. It is exposed at /sys/kernel/btf/vmlinux, and Rocky and RHEL 9 ship it on by default, so you need neither kernel-devel nor debuginfo packages. You can read it yourself with bpftool: here is task_struct, the kernel's process structure, and its field real_parent at bit offset 10240, which is byte 1280. On another kernel that number is different. The same file is what bpftrace reads when you write curtask->real_parent, and bpftool turns it into vmlinux.h, the one header our BPF C files include. The next slide shows what the loader does with it.

### 17. One binary, two kernels, both correct

`core-diagram` · 1:45 min · starts at 19:30

Here is the same idea as a picture, because this is what makes a copied binary keep working. On the left, the binary is built once in CI. The BPF object inside it does not contain the byte offset of real_parent; clang left a relocation that names the field: task_struct.real_parent. On the right, the same file starts on two different kernels. Each kernel describes its own types in /sys/kernel/btf/vmlinux. In our 6.18 sandbox real_parent is at byte 1280 of a 3264-byte task_struct; Rocky 9's 5.14 kernel with its backports has a different layout. At load time libbpf looks the field up by name in that kernel's BTF and patches the real offset into the instruction, before the verifier sees it. So each kernel gets a program that is correct for it. Without CO-RE the offset from the build machine is compiled in, and on another kernel the program reads the wrong field, or the verifier rejects it, which is exactly the Rocky 9 trace_event_raw problem from the kernel-versions slide. Why it works: every modern kernel ships its own type description, and clang plus libbpf agree to match fields by name instead of by position. If a field really disappears, libbpf refuses to load, and you can test for that with bpf_core_field_exists. Ingredients: kernel BTF, which Rocky and RHEL have since 8.2 and most distros since 2020, clang, libbpf, and a vmlinux.h generated once. bpftrace does the same trick internally when you write curtask->real_parent.

### 18. BPF C in the kernel, Go in user space

### 19. One static binary, built ahead of time

`go-build` · 1:00 min · starts at 22:45

How the Go examples are built, which is the boring part that usually takes the longest to get right. Each example directory has a magefile with build, static, test and clean targets, and they all call one shared helper. The first build clones libbpfgo at the version ior uses, builds a static libbpf from it, and dumps vmlinux.h from the kernel's BTF. Then clang compiles the BPF C, and go build embeds the object. The payoff of CO-RE plus static linking is one file you can copy anywhere: no compiler, no headers, no packages on the production host, and it is already tested when the incident starts. We need exactly that for Kubernetes in a moment.

### 20. Two programs that never call each other

`talk` · 1:30 min · starts at 23:45

Example 11 used one way to get data out: a map. There are three channels, and this is the picture. Every BPF tool is two programs that never call each other. The kernel half runs on every event; the user half runs whenever it likes. They meet in the middle, in kernel memory that both sides can reach. Top row: the BPF side bumps a counter in a hash or array map, and user space reads the totals every few seconds or at the end. This is the cheapest channel because only the summary crosses. Middle row: for individual events the BPF side writes a record into a ring buffer and user space receives it, here on a Go channel; that costs more and can drop events when the reader is slow. Bottom row goes the other way: user space sets global variables like a target PID before loading, and the verifier treats them as constants, so the filter costs nothing. User space reaches all of this through the bpf() syscall and file descriptors; the ring buffer is even memory-mapped, so events are not copied. A few more details from the footer: per-CPU maps give lock-free counters on hot paths, the perf buffer is the older per-CPU event stream from before kernel 5.8, and maps can be pinned in /sys/fs/bpf to outlive the loader. And every bpftrace @variable is simply a map.

### 21. DNS latency of any program, no code change

`ex07` · 1:00 min · starts at 25:15

uprobes do for user space what kprobes do for the kernel. We hook getaddrinfo in libc, so every program that resolves names through glibc shows up with its lookup latency, a classic hidden cause of slow requests. This is also the first example that streams events instead of aggregating: the kernel half reserves a record in the ring buffer and submits it, and the Go half receives each record on a channel and decodes it. That is the middle row of the diagram on the previous slide. libbpf attaches automatically from the section name and finds libc.so.6 in /usr/lib64 on Rocky.

## Section: k8s

_Containers and the Kubernetes debug-container workflow with a static BPF binary, demo 2_

### 23. One kernel, many namespaces

`containers` · 0:45 min · starts at 27:15

Before Kubernetes, the container basics. BPF runs in the node's kernel and has no idea what a container is, so a probe sees everything on the node. To trace one container you filter on what a container is made of: its mount namespace, PID namespace or cgroup. Running a BPF tool inside a container needs privileges and access to the kernel's BTF and tracefs, which are often missing in a container's view of /sys. And modern app images are distroless, often Chainguard: no shell, no package manager, nothing. That is the setup for the workflow on the next slide.

### 24. Ephemeral debug container + static BPF binary

`k8s-workflow` · 1:30 min · starts at 28:00

The whole workflow on one slide. One: kubectl debug adds an ephemeral container to the running pod. target puts it into the app container's PID namespace so we can see its processes; the sysadmin profile makes it privileged, which loading BPF needs. The image is a small Chainguard busybox: it has a shell and tar, the app image has neither. Two: copy in the static binary. Three: ps shows the app as PID 1, and /proc/1/root/store is the app's view of its EFS volume. Four: run storeiops with that PID and path. Here we would see that fsync and close are the slow operations, which is typical for NFS because that is when dirty data goes to the server. When you exit, the programs are unloaded. The ephemeral container stays in the pod spec as terminated until the pod is replaced. The namespace's Pod Security level must allow privileged containers.

### 25. Two filters, then count

`storeiops-kernel` · 1:15 min · starts at 29:30

Medium depth on the featured example. Two global variables come from user space: the app's mount namespace and the device number of its /store file system. On every read, write, open, fsync or close, we first check the mount namespace, which throws away everything outside the app container in a few instructions. Then we turn the file descriptor into the file system it lives on, by following the task's file table to the struct file, its inode and the superblock, all with CO-RE reads. Only if both match do we record a start time; the exit handler computes latency and adds to a per-PID, per-operation stats entry. No ring buffer, so nothing can be dropped and the cost stays low even for a busy app.

### 26. From "PID 1, /store" to two numbers

`storeiops-user` · 1:15 min · starts at 30:45

The user side is mostly plumbing, and the interesting part is how little it needs. Because the debug container shares the app's PID namespace, /proc/1 is the app: stat of its ns/mnt link gives the namespace inode, and stat of /proc/1/root/store gives the device of the app's /store mount, even though the debug container has no such mount itself. The device number has a different encoding in user space and in the kernel, so it is converted. Both values go into the BPF object as globals before loading, the same trick ior uses for its PID filter. Then every second we read and clear the stats map and print it. One real gotcha we hit: containers do not have tracefs mounted, and libbpf needs it to attach tracepoints, so the tool mounts it.

### 27. The debug-container workflow, rehearsed with podman

`demo-k8s` · 4:00 min · starts at 32:00

## Section: wrap

_Cost and drops in production, LLMs, the ior + LLM demo, references_

### 28. Measure the cost, and expect losses

`overhead` · 1:15 min · starts at 36:00

The production checklist in one slide. Two practical questions from SREs: what does this cost, and can I trust the numbers? The kernel can count runs and nanoseconds per program once you enable bpf_stats; overhead.sh in the examples does this and prints the average. In the sandbox run a simple counting program cost about 130 nanoseconds per syscall. Multiply by the event rate to get the CPU cost. The second point: BPF never blocks the traced process. If user space does not read fast enough, events are dropped. The Go example in 10-overhead-drops makes this visible by reading slowly and counting failed reservations. Tools that stream every event must report drops, and you should look at them before trusting a latency percentile. Beyond that: it needs root or CAP_BPF plus CAP_PERFMON, so treat it like any other root tool, and run it on staging first.

### 29. BPF + SRE + LLM == Superpowers

`llm` · 1:30 min · starts at 37:15

This is the slide that ties it together. BPF used to have a steep learning curve: the verifier, CO-RE, the build and deployment glue. LLMs flatten it. They write the BPF C and the loader from a plain description, they know the verifier's rules and fix its error messages, and they handle the build plumbing that usually eats the afternoon. All examples in this repository were written that way and then tested on a real kernel, including finding the RHEL 9 tracepoint quirk. And on the analysis side, an LLM that gets both a syscall trace and the source code can tell you which code path produces the pattern you see. The caveat is the usual one: you stay responsible for what runs on production.

### 30. From /store syscalls to the line of code

`ior-llm` · 5:00 min · starts at 38:45

The closing demo. ior is a complete I/O syscall tracer built on exactly the ideas from today: libbpfgo, syscall tracepoints, CO-RE and a static binary built on Rocky 9. We use the same Kubernetes workflow as with storeiops: upload the static ior binary into the debug container, trace the app's process for a minute and write every file syscall with its duration and file name as CSV, keep the /store lines, and copy the file out. Then hand the trace and the application's source code to an LLM and ask which code paths produce the pattern. Check which PID ior expects in the debug container before the talk: the PID inside the pod, or the node PID from a node debug container. Prepare a recorded trace as a fallback.

### 31. Inspect loaded BPF programs with bpftool

`inspect` · 1:00 min · starts at 43:45

One more tool before the references, because sooner or later you want to know what BPF is running on a box, yours or somebody else's. bpftool asks the kernel. prog show lists every loaded program with its type, name, load time, the maps it uses and the process that loaded it. map show lists the maps, and map dump reads one from the outside while the tool is running, which is handy for debugging your own tool. perf show tells you which process attached to which tracepoint, kprobe or uprobe. prog dump xlated prints the bytecode the verifier accepted; dump jited shows the machine code. On our Rocky 9.9 test box 12 of the 14 loaded programs were systemd's own cgroup programs, so filter by name. Monitoring agents and security tools load BPF programs too. Programs disappear when the loader exits, unless they were pinned under /sys/fs/bpf. On Rocky 9 bpftool is one package, and unlike bpftrace it needs no compiler.

Two books and two sites. Liz Rice's Learning eBPF is short and current and explains the mechanics we covered today, including the verifier, maps and CO-RE. Brendan Gregg's BPF Performance Tools is the reference for what to measure and which tool answers which question.
