## Section: basics

_What BPF is, how programs and user space talk, why it is safe, what it costs_

### 2. "What is this process doing right now, and why is it slow?"

`why-bpf` · 2:00 min · starts at 0:30

Start with the question every on-call engineer asks. Most of us reach for iostat, vmstat and top first, and we should: they are cheap and installed everywhere. But they read counters and print averages for the whole box or the whole device. They tell you that the disk is slow or the run queue is long, not which process, file or request, and an average hides exactly the outliers that cause timeouts. strace does show individual syscalls, but through ptrace, which stops the target on every syscall and can slow it down many times over: careful on a busy production process. perf is great for busy on CPU, weaker for waiting on something. BPF answers the follow-up question at the event level, with distributions instead of averages and without restarting anything, which is why each row has a BPF counterpart, several of them in today's examples.

### 3. Small programs the kernel runs when something happens

`what` · 1:30 min · starts at 2:30

What it is, and the name in one go. Think of it as JavaScript for the kernel: instead of patching the kernel, loading a module or rebooting, you attach a small sandboxed program to an event. Three properties matter: it is event-driven, the verifier makes it safe, and the JIT makes it fast. That combination is what makes it usable on production machines. On the name: BPF was invented at Berkeley Lab in 1992 to filter packets cheaply, and tcpdump still compiles its filters to classic BPF. In 2014 Alexei Starovoitov's extended BPF landed in Linux 3.18 and turned it into a general-purpose in-kernel VM. Nobody writes classic BPF any more, so BPF and eBPF mean the same thing today, and the instruction set is now an IETF standard. Windows has a port in progress with different hooks, so everything in this talk is Linux, and the examples target Rocky Linux 9.9.

### 4. A small virtual machine inside the kernel

`vm` · 1:30 min · starts at 4:00

This is where the program actually lives. The loader in user space hands bytecode to the kernel with the bpf() syscall. Inside the kernel it lands in a small virtual machine: eleven registers, a 512-byte stack, no unbounded loops. The verifier walks every path first; only then does the JIT turn it into native machine code. Hooks such as uprobes in your app, kprobes, tracepoints, network and scheduler events trigger it. The program can only touch the outside world in two ways: helpers, a fixed list of kernel functions it is allowed to call, and maps, memory it shares with user space. Maps hold totals and state, like counters and histograms; a ring buffer map streams one record per event, which is how you share content such as file names or request details rather than just numbers. Your tool reads maps with the same bpf() syscall and the ring buffer through mmap, so events are not copied. That sandbox is why you can run this on production hosts. Think of it in two phases: once, at load time, compile, load, verify, JIT and attach; then every time the event fires, the program runs, writes into a map or the ring buffer, and your tool reads it.

### 5. C or Rust in the kernel, any language in user space

`languages` · 0:30 min · starts at 5:30

Whatever you write, it ends up as the same BPF bytecode. On the kernel side that is C with a lot of restrictions, which is why people call it pseudo C: no standard library, a tiny stack, no unbounded loops, and the verifier has to be able to prove every memory access is safe. The one real alternative for the kernel side is Rust, through Aya, which compiles Rust to BPF with its own linker. GCC can also compile C to BPF, next to clang. bpftrace has its own little language and generates the bytecode for you. Go is not a kernel-side option: there is no Go-to-BPF compiler, so libbpfgo and cilium/ebpf load a program written in C and compiled with clang; cilium/ebpf can also assemble raw BPF instructions from Go, but nobody writes real tools that way. On the user side any language that can make the bpf() syscall works; libbpf in C is the reference, and libbpfgo wraps it for Go, which is what ior and our examples use. bcc is the older approach: Python with embedded C that is compiled on every host at startup.

### 6. No eBPF there, but DTrace

`dtrace` · 0:45 min · starts at 6:00

A question I always get: what about the other Unixes? eBPF is Linux only. FreeBSD and macOS only have classic BPF, the Berkeley Packet Filter that tcpdump uses, and Solaris and illumos have no eBPF either; FreeBSD had an eBPF port as a 2018 work in progress, but it is not something you can use there. What those systems have is DTrace, which Sun built for Solaris 10 in 2005 and which inspired much of what bpftrace looks like. FreeBSD ships it in base with full kernel support. macOS ships dtrace and dtruss, but System Integrity Protection blocks most of it unless you partly disable SIP from recovery mode, and it cannot trace Rosetta processes. DTrace is a capable tracer, but it is only a tracer; eBPF is a general in-kernel virtual machine that also does networking, security and scheduling. Gregg summed it up in 2018 as: eBPF does more. Windows, for completeness, has its own eBPF port from Microsoft.

### 7. What the kernel checks, and what it cannot

`verifier` · 1:00 min · starts at 6:45

The verifier is what makes BPF safe enough for production, so it is worth knowing what it does. It simulates the program on every path, which is why loops must be bounded and why big programs fail with a complexity error. It checks every memory access and forces you to handle a failed map lookup. What it proves is that your program cannot crash the kernel or hang it. It does not stop a correct program from being expensive: attaching to a very hot event, allocating a map with millions of entries, or making all CPUs fight over one lock or one shared counter is all allowed. Those are the ways BPF tools hurt production boxes in practice.

### 8. Where you can attach a program

`hooks` · 0:45 min · starts at 7:45

For observability the top row matters most. Tracepoints are a stable interface the kernel promises to keep; kprobes can hook nearly any kernel function but may break across kernel versions. uprobes do the same for user-space code. The bottom row shows eBPF is not only for tracing: Cilium, Katran and others run networking and security in eBPF too. Today we use the top row: tracepoints in most examples, a kprobe in example 06, a uprobe in example 07. The next slide shows where the lists of all of these live.

### 9. Use the kernel's hooks, or make your own

`tracepoints` · 1:30 min · starts at 8:30

Tracepoints first. A tracepoint is a call that kernel developers placed in the code on purpose, like trace_block_rq_issue when a block request goes to the device. Its name and arguments are part of a promise not to change them lightly, and each one has a format file describing its fields. When nobody is attached, the call is patched out by a static key and costs essentially nothing. There are a few thousand of them: every syscall, the scheduler, block, network, the file systems. You can list them yourself: bpftrace -l only reads these files: the format files under tracefs, available_filter_functions for kprobe and fentry targets, the kernel's BTF for types, and ELF symbols and notes for uprobes and USDT. In a container tracefs is usually not mounted, which comes back in the Kubernetes part. If tracepoints cover your question, use them. If not, there is a ladder. First look for a nearby tracepoint, because the syscall or block request around the code you care about is often enough. Second, fentry and fexit: attach to the entry or return of any kernel function that is not inlined, with typed arguments from BTF; this is the cheapest dynamic hook and it works on Rocky 9. Third, the classic kprobe and kretprobe on the same functions, which also work on kernels without BTF. Fourth, a kprobe at an offset inside a function, which is precise but valid for one kernel build only. What you cannot hook: functions the compiler inlined, and functions marked notrace or on the kprobe blacklist; for those, probe the caller.

### 10. uprobes and USDT: tracing your own code

`uprobes` · 1:00 min · starts at 10:00

Everything so far was the kernel. uprobes do the same for user space: put a probe on any function in a binary or shared library, with no code change and no restart. For compiled languages, C, C++, Rust and Go, that works on any function symbol, as long as the binary is not stripped. One trap with Go: do not use uretprobes. The return probe rewrites the return address on the stack, and when Go grows and moves a goroutine stack the runtime finds that address and kills the process with unknown caller pc; the Go issue for it has been open since 2017. Put uprobes on the function's RET instructions instead. Shared libraries are the sweet spot: one probe on getaddrinfo in libc covers every program, that is example 07, and a probe on SSL_write in OpenSSL shows data before it is encrypted. For JIT-compiled and interpreted languages a uprobe has nothing stable to attach to, because the code is generated at run time. So the runtimes ship USDT probes, static markers compiled in, the same ones DTrace uses. HotSpot has probes for GC, class loading, threads and compilation; method entry and object allocation need -XX:+ExtendedDTraceProbes and are slow. CPython has function entry and return and GC markers if it was built with --with-dtrace; check with readelf -n for stapsdt notes. bpftrace -l lists what a binary offers. Remember the cost: each uprobe hit is a trap into the kernel, microseconds, so not on malloc.

### 11. Two programs that never call each other

`talk` · 1:30 min · starts at 11:00

Before the details on the next slide, the picture. Every BPF tool is two programs that never call each other. The kernel half runs on every event; the user half runs whenever it likes. They meet in the middle, in kernel memory that both sides can reach. Top row: the BPF side bumps a counter in a hash or array map, and user space reads the totals every few seconds or at the end. This is the cheapest channel because only the summary crosses. Middle row: for individual events the BPF side writes a record into a ring buffer and user space receives it, here on a Go channel; that costs more and can drop events when the reader is slow. Bottom row goes the other way: user space sets global variables like a target PID before loading, and the verifier treats them as constants, so the filter costs nothing. User space reaches all of this through the bpf() syscall and file descriptors; the ring buffer is even memory-mapped, so events are not copied. A few more details from the footer: per-CPU maps give lock-free counters on hot paths, the perf buffer is the older per-CPU event stream from before kernel 5.8, and maps can be pinned in /sys/fs/bpf to outlive the loader. And every bpftrace @variable is simply a map.

### 12. Measure the cost, and expect losses

`overhead` · 1:15 min · starts at 12:30

Two practical questions from SREs: what does this cost, and can I trust the numbers? The kernel can count runs and nanoseconds per program once you enable bpf_stats; overhead.sh in the examples does this and prints the average. In the sandbox run a simple counting program cost about 130 nanoseconds per syscall. Multiply by the event rate to get the CPU cost. The second point: BPF never blocks the traced process. If user space does not read fast enough, events are dropped. The Go example in 10-overhead-drops makes this visible by reading slowly and counting failed reservations. Tools that stream every event must report drops, and you should look at them before trusting a latency percentile.

### 14. bpftrace is a compiler that runs on your host

`bpftrace-inside` · 1:15 min · starts at 14:15

Before we move on from bpftrace, it helps to know what it actually does when you press enter, because that explains when not to use it. bpftrace is a complete compiler. It parses your script, resolves tracepoint arguments and kernel types from tracefs and BTF, generates LLVM IR, lets LLVM optimise it and emit BPF bytecode, and then does what every loader does: the bpf() syscall, verifier, JIT, attach. When you press Ctrl-C it reads the maps and prints them. You can watch the stages with bpftrace -d all, or keep the IR with --emit-llvm. All of this happens on the host you are tracing, every time you start a script. In our sandbox the bpftrace binary pulls in about 160 MB of LLVM and Clang libraries; a small script compiles in a fraction of a second at about 80 MB resident. That is a great trade for interactive exploration, which is what bpftrace is for.

## Section: portable

_Kernel versions, CO-RE, why not a compiler in production, and the Go examples with libbpfgo_

### 18. Your BPF code vs. the kernel it lands on

`kernel-versions` · 1:00 min · starts at 18:45

This is the problem CO-RE solves, so state it clearly. A BPF program that reads kernel memory needs to know where things are, and that changes between kernels. Function names change and kprobes fail to attach; struct layouts change and hard-coded offsets read garbage. A real example we hit with ior and in these examples: RHEL 9 backports a patch that adds a field to the common trace entry, so the BTF type trace_event_raw_sys_enter is 8 bytes wider than what the kernel really passes to a syscall tracepoint program. Programs that use it read past the context and the verifier rejects them with EACCES on stock Rocky 9. Using struct syscall_trace_enter, as bcc and ior now do, fixes it; every example here does that. RHEL makes the version number misleading because Red Hat backports a lot of BPF into 5.14, so probe features rather than comparing versions. bcc's answer was to ship C source and compile it on each host against that host's kernel headers, which is why bcc-tools on Rocky needs kernel-devel for the exact running kernel, and why it is slow to start.

### 19. The kernel describes its own types

`btf` · 1:15 min · starts at 19:45

CO-RE only works because the kernel carries a description of itself. That description is BTF, the BPF Type Format: a compact encoding of every type in the kernel, so every struct, every field with its offset, and every function signature. It is produced from the debug info when the kernel is built and exposed at /sys/kernel/btf/vmlinux. Rocky and RHEL 9 ship it on by default, so you need neither kernel-devel nor debuginfo packages. On our sandbox kernel it is 5.5 MB and describes about 126,000 types. You can read it yourself with bpftool: here task_struct, and real_parent at bit offset 10240, which is byte 1280, exactly the number libbpf will patch into our program on this kernel. The same command with format c writes vmlinux.h, one header with every kernel type, which our BPF C files include instead of kernel headers. bpftrace reads the same file when you write curtask->real_parent. The next slide shows how libbpf uses it at load time.

### 20. One binary, two kernels, both correct

`core-diagram` · 1:45 min · starts at 21:00

Here is the same idea as a picture, because this is what makes a copied binary keep working. On the left, the binary is built once in CI. The BPF object inside it does not contain the byte offset of real_parent; clang left a relocation that names the field: task_struct.real_parent. On the right, the same file starts on two different kernels. Each kernel describes its own types in /sys/kernel/btf/vmlinux. In our 6.18 sandbox real_parent is at byte 1280 of a 3264-byte task_struct; Rocky 9's 5.14 kernel with its backports has a different layout. At load time libbpf looks the field up by name in that kernel's BTF and patches the real offset into the instruction, before the verifier sees it. So each kernel gets a program that is correct for it. Without CO-RE the offset from the build machine is compiled in, and on another kernel the program reads the wrong field, or the verifier rejects it, which is exactly the Rocky 9 trace_event_raw problem from the kernel-versions slide. Why it works: every modern kernel ships its own type description, and clang plus libbpf agree to match fields by name instead of by position. If a field really disappears, libbpf refuses to load, and you can test for that with bpf_core_field_exists. Ingredients: kernel BTF, which Rocky and RHEL have since 8.2 and most distros since 2020, clang, libbpf, and a vmlinux.h generated once. bpftrace does the same trick internally when you write curtask->real_parent.

### 21. A compiler on every production host?

`compiler-vs-core` · 1:00 min · starts at 22:45

This is the reason the rest of the examples are Go programs. bpftrace and bcc compile on the target host: you need the compiler libraries installed on every production box, bcc even needs kernel headers that match the running kernel exactly, the compile runs on a machine that is already in trouble, and the program is whatever someone typed, running as root. Many security teams will not allow a compiler on production hosts, and minimal container images simply do not have one. With CO-RE the compile happens once, in CI. The binary carries the BPF object, libbpf reads the running kernel's BTF, fixes up the struct offsets and loads it. Nothing else has to be installed on the host, the code was reviewed like any other tool, and it starts in milliseconds. So: bpftrace to explore, then turn what you learned into a small reviewed Go tool. The next slides are exactly that, one example at a time.

### 23. mage, go:embed and a static binary

`go-build` · 0:45 min · starts at 25:00

How the Go examples are built, which is the boring part that usually takes the longest to get right. Each example directory has a magefile with build, static, test and clean targets, and they all call one shared helper. The first build clones libbpfgo at the version ior uses, builds a static libbpf from it, and dumps vmlinux.h from the kernel's BTF. Then clang compiles the BPF C, and go build embeds the object. ### 24. DNS latency of any program, no code change

`ex07` · 1:00 min · starts at 25:45

## Section: k8s

_Containers and the Kubernetes debug-container workflow with a static BPF binary, demo 2_

### 27. One kernel, many namespaces

`containers` · 0:45 min · starts at 28:45

Before Kubernetes, the container basics. BPF runs in the node's kernel and has no idea what a container is, so a probe sees everything on the node. To trace one container you filter on what a container is made of: its mount namespace, PID namespace or cgroup. Running a BPF tool inside a container needs privileges and access to the kernel's BTF and tracefs, which are often missing in a container's view of /sys. And modern app images are distroless, often Chainguard: no shell, no package manager, nothing. That is the setup for the workflow on the next slide.

### 28. Ephemeral debug container + static BPF binary

`k8s-workflow` · 1:30 min · starts at 29:30

The whole workflow on one slide. One: kubectl debug adds an ephemeral container to the running pod. target puts it into the app container's PID namespace so we can see its processes; the sysadmin profile makes it privileged, which loading BPF needs. The image is a small Chainguard busybox: it has a shell and tar, the app image has neither. Two: copy in the static binary. Three: ps shows the app as PID 1, and /proc/1/root/store is the app's view of its EFS volume. Four: run storeiops with that PID and path. Here we would see that fsync and close are the slow operations, which is typical for NFS because that is when dirty data goes to the server. When you exit, the programs are unloaded. The ephemeral container stays in the pod spec as terminated until the pod is replaced. The namespace's Pod Security level must allow privileged containers.

### 29. Two filters, then count

`storeiops-kernel` · 1:15 min · starts at 31:00

Medium depth on the featured example. Two global variables come from user space: the app's mount namespace and the device number of its /store file system. On every read, write, open, fsync or close, we first check the mount namespace, which throws away everything outside the app container in a few instructions. Then we turn the file descriptor into the file system it lives on, by following the task's file table to the struct file, its inode and the superblock, all with CO-RE reads. Only if both match do we record a start time; the exit handler computes latency and adds to a per-PID, per-operation stats entry. No ring buffer, so nothing can be dropped and the cost stays low even for a busy app.

### 30. From "PID 1, /store" to two numbers

`storeiops-user` · 1:15 min · starts at 32:15

The user side is mostly plumbing, and the interesting part is how little it needs. Because the debug container shares the app's PID namespace, /proc/1 is the app: stat of its ns/mnt link gives the namespace inode, and stat of /proc/1/root/store gives the device of the app's /store mount, even though the debug container has no such mount itself. The device number has a different encoding in user space and in the kernel, so it is converted. Both values go into the BPF object as globals before loading, the same trick ior uses for its PID filter. Then every second we read and clear the stats map and print it. One real gotcha we hit: containers do not have tracefs mounted, and libbpf needs it to attach tracepoints, so the tool mounts it.

### 31. The debug-container workflow, rehearsed with podman

`demo-k8s` · 4:00 min · starts at 33:30

Second demo, about five minutes. Build the static binary before the talk. podman-demo.sh reproduces the Kubernetes setup on one Rocky box: an app container writing to a /store volume, a privileged debug container in the app's PID namespace, a podman cp of the binary, and then storeiops tracing PID 1. Point out that the reads of /etc/os-release by the same app never show up, because they are not on /store, and that nothing from the host appears either. If you have a cluster, do the real kubectl version instead.

## Section: wrap

_Production checklist, LLMs, the ior + LLM demo, reading_

### 32. Before you run it on a production box

`production` · 0:45 min · starts at 37:30

Practical checklist. Start with a short -duration and a PID filter, watch the host's CPU while tracing, and prefer aggregation over per-event output on hot paths. Most modern distributions ship BTF-enabled kernels (RHEL 8.2+, Ubuntu 20.10+, recent Debian and Fedora), but check before an incident, not during one: run examples/run-all.sh on a representative box now. In Kubernetes, the namespace must allow a privileged debug container, which is worth arranging with the platform team before you need it.

### 33. BPF + SRE + LLM == God

`llm` · 1:30 min · starts at 38:15

This is the slide that ties it together. BPF used to have a steep learning curve: the verifier, CO-RE, the build and deployment glue. LLMs flatten it. They write the BPF C and the loader from a plain description, they know the verifier's rules and fix its error messages, and they handle the build plumbing that usually eats the afternoon. All examples in this repository were written that way and then tested on a real kernel, including finding the RHEL 9 tracepoint quirk. And on the analysis side, an LLM that gets both a syscall trace and the source code can tell you which code path produces the pattern you see. The caveat is the usual one: you stay responsible for what runs on production.

### 34. From /store syscalls to the line of code

`ior-llm` · 5:00 min · starts at 39:45

The closing demo. ior is a complete I/O syscall tracer built on exactly the ideas from today: libbpfgo, syscall tracepoints, CO-RE and a static binary built on Rocky 9. We use the same Kubernetes workflow as with storeiops: upload the static ior binary into the debug container, trace the app's process for a minute and write every file syscall with its duration and file name as CSV, keep the /store lines, and copy the file out. Then hand the trace and the application's source code to an LLM and ask which code paths produce the pattern. Check which PID ior expects in the debug container before the talk: the PID inside the pod, or the node PID from a node debug container. Prepare a recorded trace as a fallback.

### 35. BPF references

`reading` · 0:45 min · starts at 44:45

Two books and two sites. Liz Rice's Learning eBPF is short and current and explains the mechanics we covered today, including the verifier, maps and CO-RE. Brendan Gregg's BPF Performance Tools is the reference for what to measure and which tool answers which question. Below them: the kernel's own BPF documentation, the bpftrace site with its reference guide, and libbpfgo, the Go library the examples use.
