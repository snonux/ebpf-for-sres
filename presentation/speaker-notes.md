## Section: basics

_What BPF is, how programs and user space talk, why it is safe, what it costs_

### 2. "What is this process doing right now, and why is it slow?"

`question` · 1:00 min · starts at 0:30

Start with the question every on-call engineer asks. Classic tools each have a blind spot. strace is the one most people know, but it works via ptrace and pauses the target on every syscall, which is why you should be careful running it on a busy production process. eBPF lets you ask new questions of a running system without restarting anything.

### 3. BPF, eBPF, and now just BPF

`name` · 1:00 min · starts at 1:30

Quick history so the names stop being confusing. BPF was invented at Berkeley Lab in 1992 to filter packets cheaply in the kernel, and tcpdump still compiles its filter expressions to classic BPF. In 2014 Alexei Starovoitov's extended BPF landed in Linux 3.18 and turned it into a general-purpose in-kernel VM. Nobody writes classic BPF any more, so BPF and eBPF mean the same thing today. Windows has a port in progress (eBPF for Windows), but the hooks there are different, so everything in this talk is Linux, and the examples target Rocky Linux 9.9.

### 4. Small programs the kernel runs when something happens

`what` · 0:45 min · starts at 2:30

Now that the name is out of the way: what it is. Three properties matter: it is event-driven, the verifier makes it safe, and the JIT makes it fast. That combination is what makes it usable on production machines, unlike loading a custom kernel module.

### 5. From source code to a running probe

`lifecycle` · 1:15 min · starts at 3:15

Two phases. At load time, user space compiles and loads the program and the kernel's verifier decides whether it is allowed to run; if it is, the JIT turns it into native code and it is attached to a hook. After that, every time the event fires, the program runs inside the kernel, writes into a map or ring buffer, and your user-space tool reads from there. Light boxes are user space, dark boxes are the kernel.

### 6. Pseudo C in the kernel, any language in user space

`languages` · 0:45 min · starts at 4:30

Whatever you write, it ends up as the same BPF bytecode. On the kernel side that is C with a lot of restrictions, which is why people call it pseudo C: no standard library, a tiny stack, no unbounded loops, and the verifier has to be able to prove every memory access is safe. Rust is an option through Aya. bpftrace generates the bytecode for you. On the user side any language that can make the bpf() syscall works; libbpf in C is the reference, and libbpfgo wraps it for Go, which is what ior and our examples use. bcc is the older approach: Python with embedded C that is compiled on every host at startup.

### 7. What the kernel checks, and what it cannot

`verifier` · 1:15 min · starts at 5:15

The verifier is what makes BPF safe enough for production, so it is worth knowing what it does. It simulates the program on every path, which is why loops must be bounded and why big programs fail with a complexity error. It checks every memory access and forces you to handle a failed map lookup. What it proves is that your program cannot crash the kernel or hang it. It does not stop a correct program from being expensive: attaching to a very hot event, allocating a map with millions of entries, or making all CPUs fight over one lock or one shared counter is all allowed. Those are the ways BPF tools hurt production boxes in practice.

### 8. Where you can attach a program

`hooks` · 1:00 min · starts at 6:30

For observability the top row matters most. Tracepoints are a stable interface the kernel promises to keep; kprobes can hook nearly any kernel function but may break across kernel versions. uprobes do the same for user-space code. The bottom row shows eBPF is not only for tracing: Cilium, Katran and others run networking and security in eBPF too. Today we use the top row: tracepoints in most examples, a kprobe in example 06, a uprobe in example 07. The next slide shows where the lists of all of these live.

### 9. It is all in tracefs, sysfs and ELF

`probes-sysfs` · 0:45 min · starts at 7:30

bpftrace -l is not magic: it reads the same files you can read with cat. Every tracepoint has a format file describing its arguments with offsets, and that is where args.filename comes from. available_filter_functions lists the tens of thousands of kernel functions you could kprobe. The BTF file describes every kernel struct. For user space, probes come from the ELF symbol table, and USDT probes from ELF notes. On Rocky 9, tracefs is mounted at /sys/kernel/tracing. Inside a container it usually is not, which will come back in the Kubernetes part.

### 10. Two programs, and how they talk

`maps` · 1:15 min · starts at 8:15

Every BPF tool is two programs: the BPF object in the kernel and a loader in user space. They never call each other; they share maps. A map is a kernel data structure with a file descriptor: the BPF side updates it with helpers, user space reads it with the bpf() syscall. Aggregating in a hash map is cheapest because only the summary crosses over. A ring buffer streams individual events when you need them all, at a higher cost. Global variables go the other way: user space writes them before loading, and because they are const volatile, the verifier treats them as constants. All of our Go examples use exactly these calls.

### 11. Measure the cost, and expect losses

`overhead` · 1:15 min · starts at 9:30

Two practical questions from SREs: what does this cost, and can I trust the numbers? The kernel can count runs and nanoseconds per program once you enable bpf_stats; overhead.sh in the examples does this and prints the average. In the sandbox run a simple counting program cost about 130 nanoseconds per syscall. Multiply by the event rate to get the CPU cost. The second point: BPF never blocks the traced process. If user space does not read fast enough, events are dropped. The Go example in 10-overhead-drops makes this visible by reading slowly and counting failed reservations. Tools that stream every event must report drops, and you should look at them before trusting a latency percentile.

### 13. Opens per process, three ways

`ex01` · 0:45 min · starts at 11:15

The command from the cover slide, in the three flavours every example in the repository comes in. bpftrace is one line. SystemTap looks similar but compiles a kernel module. ### 14. Who is opening which files?

`oneliner-open` · 0:30 min · starts at 12:00

This is essentially opensnoop in one line. The probe fires when any process enters the openat syscall. comm is the process name, args.filename is a pointer into user memory, and str() copies the string out safely. Useful in incidents: which process keeps touching that config file, is something hammering /proc, is a service reading certificates on every request? We saw where args.filename comes from on the probes slide. Unlike the counters, this prints one line per event, so the Go version of it streams events through a ring buffer.

### 15. Syscalls per process, counted in the kernel

`ex03` · 0:30 min · starts at 12:30

Swap one probe and the same three lines answer a different question: which process is making the most syscalls. Note that nothing is printed per event: the counting happens in a kernel map and only the summary crosses into user space when you press Ctrl-C. That is why this is safe to run on a busy host. The output is from the sandbox test run with the workload script.

### 16. How big are the reads?

`ex04` · 0:30 min · starts at 13:00

A histogram instead of a counter. The filter between slashes runs in the kernel, so failed reads never touch the map. In the C and Go version the histogram is an array map with 64 slots and a bounded loop computes the log2 bucket, which the verifier accepts because the loop has a fixed upper bound. The Go program prints it in bpftrace's format, which is what you see here.

### 17. Latency: time from entry to return

`oneliner-latency` · 0:45 min · starts at 13:30

This is the core pattern of latency tracing. The @start map holds one timestamp per thread; the exit tracepoint computes the delta and feeds a histogram in microseconds, then deletes the entry so the map does not grow. Keep this pattern in mind: it is exactly what ior does, with the same syscall tracepoints, except ior does the pairing in user space rather than in a BPF map. The next slide does the same with a kprobe.

### 18. Hook any kernel function, at a price

`ex06` · 0:45 min · starts at 14:15

Same latency pattern as example 05, but on a kernel function instead of a syscall tracepoint. kprobes can go almost anywhere, which is their power, and they are tied to one kernel build, which is their price. On Rocky 9 vfs_read is a stable, non-inlined function, so this example works, but it is exactly the kind of probe that breaks on an upgrade. The C version uses the BPF_KPROBE macros from libbpf, which hide the register access. In the sandbox this one could not run because that kernel has no kprobe support at all, which is a nice reminder to check before an incident.

### 19. DNS latency of any program, no code change

`ex07` · 0:45 min · starts at 15:00

uprobes do for user space what kprobes do for the kernel. Here we hook getaddrinfo in libc, so every program that resolves names through glibc shows up with its lookup latency, which is a classic hidden cause of slow requests. The Go version uses libbpf's automatic attach: the section name says libc.so.6:getaddrinfo and libbpf finds the library in /usr/lib64 on Rocky. Be careful with uprobes on hot functions: each hit is a trap into the kernel and costs microseconds, so probing malloc in a busy service is a bad idea.

## Section: portable

_Kernel versions, CO-RE, and small Go tools with libbpfgo_

### 21. Your BPF code vs. the kernel it lands on

`kernel-versions` · 1:00 min · starts at 18:45

This is the problem CO-RE solves, so state it clearly. A BPF program that reads kernel memory needs to know where things are, and that changes between kernels. Function names change and kprobes fail to attach; struct layouts change and hard-coded offsets read garbage. A real example we hit with ior and in these examples: RHEL 9 backports a patch that adds a field to the common trace entry, so the BTF type trace_event_raw_sys_enter is 8 bytes wider than what the kernel really passes to a syscall tracepoint program. Programs that use it read past the context and the verifier rejects them with EACCES on stock Rocky 9. Using struct syscall_trace_enter, as bcc and ior now do, fixes it; every example here does that. RHEL makes the version number misleading because Red Hat backports a lot of BPF into 5.14, so probe features rather than comparing versions. bcc's answer was to ship C source and compile it on each host against that host's kernel headers, which is why bcc-tools on Rocky needs kernel-devel for the exact running kernel, and why it is slow to start.

### 22. Compile once, run everywhere

`core` · 1:30 min · starts at 19:45

CO-RE is the key idea that makes modern BPF tools deployable. Instead of compiling an offset into the program, clang records what you meant: the tgid field of the real_parent field of task_struct. At load time libbpf reads the running kernel's BTF, which is a compact description of every kernel type, finds those fields by name and patches the instructions. So the same object file loads on a Rocky 9 box and on a laptop with a 6.x kernel, and the target needs neither compiler nor kernel headers. Combine that with a static binary and deployment becomes copying one file. bpftrace does the same trick internally when you write curtask->real_parent.

### 23. Every exec, with its parent

`ex12` · 0:45 min · starts at 21:15

A small execsnoop: who starts which program, and from which parent. The parent PID is not a tracepoint argument, so we have to walk kernel structs: from the current task to its real_parent and its tgid. In bpftrace this is just pointer syntax, resolved through BTF. In C it is BPF_CORE_READ, which turns into relocations. The C version uses a tp_btf program: the same tracepoint, but its arguments are typed kernel pointers described by BTF, so even the filename comes through CO-RE, and it needs no tracefs. This object was built in an Ubuntu sandbox on a 6.18 kernel and the same file is meant to load unchanged on Rocky 9's 5.14. Short-lived processes spawning in a loop are a classic source of CPU load that top never shows; this is the tool for it.

### 24. BPF C in the kernel, Go in user space

`ex11` · 1:30 min · starts at 22:00

This is the anatomy of every Go example in the repository, and of ior. On the left the kernel half: a map declaration and a function with a SEC name that says where to attach it. On the right the user half with libbpfgo: embed the compiled object into the binary, open it, load it (this is when the verifier runs, and where you get its log if it refuses), attach every program to the hook its section names, wait, and read the map with an iterator. The same object is also loaded by a 60-line C program in the same directory, so you can compare libbpf in C with libbpfgo directly. The Go code on the slide is lightly trimmed of error handling.

### 25. mage, go:embed and a static binary

`go-build` · 1:00 min · starts at 23:30

How the Go examples are built, which is the boring part that usually takes the longest to get right. Each example directory has a magefile with build, static, test and clean targets, and they all call one shared helper. The first build clones libbpfgo at the version ior uses, builds a static libbpf from it, and dumps vmlinux.h from the kernel's BTF. Then clang compiles the BPF C, and go build embeds the object. For a fully static binary you need static libelf and zstd, which Rocky does not package, so there is a Containerfile that builds them. The payoff of CO-RE plus static linking is one file you can copy anywhere, which we need for Kubernetes in a moment.

### 26. Same shape every time, 40 to 60 lines of Go

`go-gallery` · 0:45 min · starts at 24:30

A quick flyover, not a walkthrough: the point is that once you have seen one, you have seen them all. Each one is a BPF C file and a Go file of about fifty lines. ### 27. Tools worth knowing before your next page

`toolbox` · 0:30 min · starts at 25:15

You do not have to write BPF to benefit from it. These tools ship with bcc-tools on Rocky and live in /usr/share/bcc/tools, which is not in PATH. ### 28. Where BPF fits next to stap, across many hosts

`stap-grid` · 1:00 min · starts at 25:45

Many of you know SystemTap, which did all of this years before BPF and has a richer language. The difference is the mechanism: stap translates the script to C and loads a kernel module, so the host needs a compiler, matching kernel headers, often debuginfo, and with Secure Boot a signed module. A bug can take the box down. BPF programs are verified bytecode and only need BTF, which RHEL 9 kernels have. The examples 01 to 06 have stap versions so you can compare side by side. On a large fleet the same properties matter even more: running a one-liner everywhere with a timeout through Ansible or pssh is easy, and for anything recurring, ship a static CO-RE binary instead of a toolchain.

## Section: k8s

_Containers and the Kubernetes debug-container workflow with a static BPF binary, demo 2_

### 29. One kernel, many namespaces

`containers` · 0:45 min · starts at 26:45

Before Kubernetes, the container basics. BPF runs in the node's kernel and has no idea what a container is, so a probe sees everything on the node. To trace one container you filter on what a container is made of: its mount namespace, PID namespace or cgroup. Running a BPF tool inside a container needs privileges and access to the kernel's BTF and tracefs, which are often missing in a container's view of /sys. And modern app images are distroless, often Chainguard: no shell, no package manager, nothing. That is the setup for the workflow on the next slide.

### 30. Ephemeral debug container + static BPF binary

`k8s-workflow` · 1:30 min · starts at 27:30

The whole workflow on one slide. One: kubectl debug adds an ephemeral container to the running pod. target puts it into the app container's PID namespace so we can see its processes; the sysadmin profile makes it privileged, which loading BPF needs. The image is a small Chainguard busybox: it has a shell and tar, the app image has neither. Two: copy in the static binary. Three: ps shows the app as PID 1, and /proc/1/root/store is the app's view of its EFS volume. Four: run storeiops with that PID and path. Here we would see that fsync and close are the slow operations, which is typical for NFS because that is when dirty data goes to the server. When you exit, the programs are unloaded. The ephemeral container stays in the pod spec as terminated until the pod is replaced. The namespace's Pod Security level must allow privileged containers.

### 31. Two filters, then count

`storeiops-kernel` · 1:30 min · starts at 29:00

Medium depth on the featured example. Two global variables come from user space: the app's mount namespace and the device number of its /store file system. On every read, write, open, fsync or close, we first check the mount namespace, which throws away everything outside the app container in a few instructions. Then we turn the file descriptor into the file system it lives on, by following the task's file table to the struct file, its inode and the superblock, all with CO-RE reads. Only if both match do we record a start time; the exit handler computes latency and adds to a per-PID, per-operation stats entry. No ring buffer, so nothing can be dropped and the cost stays low even for a busy app.

### 32. From "PID 1, /store" to two numbers

`storeiops-user` · 1:15 min · starts at 30:30

The user side is mostly plumbing, and the interesting part is how little it needs. Because the debug container shares the app's PID namespace, /proc/1 is the app: stat of its ns/mnt link gives the namespace inode, and stat of /proc/1/root/store gives the device of the app's /store mount, even though the debug container has no such mount itself. The device number has a different encoding in user space and in the kernel, so it is converted. Both values go into the BPF object as globals before loading, the same trick ior uses for its PID filter. Then every second we read and clear the stats map and print it. One real gotcha we hit: containers do not have tracefs mounted, and libbpf needs it to attach tracepoints, so the tool mounts it.

### 33. The debug-container workflow, rehearsed with podman

`demo-k8s` · 4:00 min · starts at 31:45

Second demo, about five minutes. Build the static binary before the talk. podman-demo.sh reproduces the Kubernetes setup on one Rocky box: an app container writing to a /store volume, a privileged debug container in the app's PID namespace, a podman cp of the binary, and then storeiops tracing PID 1. Point out that the reads of /etc/os-release by the same app never show up, because they are not on /store, and that nothing from the host appears either. If you have a cluster, do the real kubectl version instead.

## Section: wrap

_Production checklist, LLMs, the ior + LLM demo, reading, next steps_

### 34. Before you run it on a production box

`production` · 1:00 min · starts at 35:45

Practical checklist. Start with a short -duration and a PID filter, watch the host's CPU while tracing, and prefer aggregation over per-event output on hot paths. Most modern distributions ship BTF-enabled kernels (RHEL 8.2+, Ubuntu 20.10+, recent Debian and Fedora), but check before an incident, not during one: run examples/run-all.sh on a representative box now. In Kubernetes, the namespace must allow a privileged debug container, which is worth arranging with the platform team before you need it.

### 35. BPF + SRE + LLM == God

`llm` · 1:30 min · starts at 36:45

This is the slide that ties it together. BPF used to have a steep learning curve: the verifier, CO-RE, the build and deployment glue. LLMs flatten it. They write the BPF C and the loader from a plain description, they know the verifier's rules and fix its error messages, and they handle the build plumbing that usually eats the afternoon. All examples in this repository were written that way and then tested on a real kernel, including finding the RHEL 9 tracepoint quirk. And on the analysis side, an LLM that gets both a syscall trace and the source code can tell you which code path produces the pattern you see. The caveat is the usual one: you stay responsible for what runs on production.

### 36. From /store syscalls to the line of code

`ior-llm` · 5:00 min · starts at 38:15

The closing demo. ior is a complete I/O syscall tracer built on exactly the ideas from today: libbpfgo, syscall tracepoints, CO-RE and a static binary built on Rocky 9. We use the same Kubernetes workflow as with storeiops: upload the static ior binary into the debug container, trace the app's process for a minute and write every file syscall with its duration and file name as CSV, keep the /store lines, and copy the file out. Then hand the trace and the application's source code to an LLM and ask which code paths produce the pattern. Check which PID ior expects in the debug container before the talk: the PID inside the pod, or the node PID from a node debug container. Prepare a recorded trace as a fallback.

### 37. Two books and a few links

`reading` · 0:30 min · starts at 43:15

Two books. Brendan Gregg's BPF Performance Tools is the reference for what to measure and which tool answers which question; it predates CO-RE becoming mainstream but the methodology has not aged. Liz Rice's Learning eBPF is shorter and newer and explains the mechanics we covered today, including CO-RE. Andrii Nakryiko's blog is the best source on CO-RE and libbpf.
