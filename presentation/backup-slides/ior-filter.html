ior filtering

Filter in the kernel, configure from Go

const volatile u32 PID_FILTER = -1;  // set before load
const volatile u32 TID_FILTER = -1;

static __always_inline int filter(__u32 *pid, __u32 *tid) {
    u64 pid_tgid = bpf_get_current_pid_tgid();
    *pid = pid_tgid >> 32;
    if (*pid == IOR_PID_FILTER) return FILTER; // skip ior
    *tid = pid_tgid & 0xFFFFFFFF;
    if (-1 == PID_FILTER || *pid == PID_FILTER)
        if (-1 == TID_FILTER || *tid == TID_FILTER)
            return ACCEPT;
    return FILTER;
}

// Go, before the kernel sees the program
m.InitGlobalVariable("PID_FILTER", uint32(cfg.PidFilter))
m.InitGlobalVariable("TID_FILTER", uint32(cfg.TidFilter))
m.BPFLoadObject()  // the verifier runs here

const volatile globals are read-only for the BPF program but patched by user space before loading.

ior filters out its own PID, so it never traces itself in a loop.

sudo ior -pid 1234

From internal/c/filter.c, flags.h and internal/bpfsetup.go. The globals are declared const volatile: const lets the verifier treat them as constants and prune dead branches, volatile stops the compiler from optimising them away. libbpfgo's InitGlobalVariable writes the values into the object's read-only data section before BPFLoadObject hands it to the kernel. The payoff: when you trace one PID, events from every other process are discarded in a few instructions and never touch the ring buffer.
