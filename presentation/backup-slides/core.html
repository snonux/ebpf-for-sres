CO-RE

Compile once, run everywhere

Build host, once

e->ppid = BPF_CORE_READ(task,
            real_parent, tgid);

clang records a relocation: "task_struct → real_parent → tgid", not a number.

→

foo.bpf.o

insn 12: load [r1 + ?]
  reloc: task_struct.real_parent
insn 14: load [r2 + ?]
  reloc: task_struct.tgid

→

Each target host, at load

libbpf + kernel BTF

Looks the fields up by name in /sys/kernel/btf/vmlinux and patches the real offsets in before the verifier runs.

Ingredients

Kernel BTF (Rocky/RHEL 8.2+, most distros since 2020), clang, libbpf, and a vmlinux.h generated once.

Result

One .bpf.o for Rocky 9's 5.14 and for a 6.x kernel. No compiler or headers on the target.

Plus static linking

Embed the object in a static Go binary: one file to copy anywhere. That is how ior and example 13 ship.

CO-RE is the key idea that makes modern BPF tools deployable. Instead of compiling an offset into the program, clang records what you meant: the tgid field of the real_parent field of task_struct. At load time libbpf reads the running kernel's BTF, which is a compact description of every kernel type, finds those fields by name and patches the instructions. So the same object file loads on a Rocky 9 box and on a laptop with a 6.x kernel, and the target needs neither compiler nor kernel headers. Combine that with a static binary and deployment becomes copying one file. bpftrace does the same trick internally when you write curtask->real_parent.
