Example 06 · Go, kprobes

Hook any kernel function, at a price

Re-implements this bpftrace

kprobe:vfs_read { @start[tid] = nsecs; }   kretprobe:vfs_read /@start[tid]/ { ... }

SEC("kprobe/vfs_read")
int BPF_KPROBE(vfs_read_enter) { ... }

SEC("kretprobe/vfs_read")
int BPF_KRETPROBE(vfs_read_exit) { ... }
// same body as 05: only the hook changed

Power

Any of ~50,000 kernel functions, not only the ones with a tracepoint. Sees reads from every path into the VFS.

Price

vfs_read is internal: it can be renamed, inlined or change arguments in the next kernel. Then the probe fails to attach.

examples/06-vfs-read-latency-kprobe/ · vfsreadlat.bt · vfsreadlat.stp · vfsreadlat.bpf.c + main.go

Same latency pattern as example 05, but on a kernel function instead of a syscall tracepoint. In C only the section names change, plus libbpf's BPF_KPROBE macros, which hide the register access. kprobes can go almost anywhere, which is their power, and they are tied to one kernel build, which is their price. On Rocky 9 vfs_read is a stable, non-inlined function, so this works, but it is exactly the kind of probe that breaks on an upgrade. In our sandbox this example could not run at all because that kernel has no kprobe support, which is a nice reminder to check before an incident.
