No tracepoint where you need one? Go down the list

1

Nearby tracepoint

Often good enough: the syscall or the block request around it.

tracepoint:block:block_rq_issue

2

fentry / fexit

Any non-inlined kernel function, typed args via BTF. Cheapest.

fentry:vfs_read { args.count }

3

kprobe / kretprobe

Same ~50,000 functions, older and slower; also works without BTF.

kprobe:vfs_read kretprobe:vfs_read

4

kprobe at an offset

Any instruction inside a function. Fragile: one build only.

kprobe:vfs_read+0x1a

Out of reach: inlined functions and notrace or kprobe-blacklisted ones. Then probe the caller.

Tracepoints first. A tracepoint is a call that kernel developers placed in the code on purpose, like trace_block_rq_issue when a block request goes to the device. Its name and arguments are part of a promise not to change them lightly, and each one has a format file describing its fields. When nobody is attached, the call is patched out by a static key and costs essentially nothing. There are a few thousand of them: every syscall, the scheduler, block, network, the file systems. If they cover your question, use them. If not, there is a ladder. First look for a nearby tracepoint, because the syscall or block request around the code you care about is often enough. Second, fentry and fexit: attach to the entry or return of any kernel function that is not inlined, with typed arguments from BTF; this is the cheapest dynamic hook and it works on Rocky 9. Third, the classic kprobe and kretprobe on the same functions, which also work on kernels without BTF. Fourth, a kprobe at an offset inside a function, which is precise but valid for one kernel build only. What you cannot hook: functions the compiler inlined, and functions marked notrace or on the kprobe blacklist; for those, probe the caller.
