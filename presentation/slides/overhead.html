Overhead and dropped samples

Measure the cost, and expect losses

Cost = event rate × cost per run

$ sudo sysctl kernel.bpf_stats_enabled=1
$ sudo bpftool prog show
370: tracepoint  name sys_enter
     run_time_ns 17322556 run_cnt 131702

≈ 130 ns per run for a count by process name. Tracepoints and kprobes cost about the same; uprobes trap into the kernel and cost several times more.

Drops: BPF never waits for user space

$ sudo ./drops -slow 1ms   // a slow reader
received     843   dropped  28588 events/s

When the ring buffer is full, bpf_ringbuf_reserve() fails and the event is gone. The traced app never slows down; your data gets holes. bpftrace prints Lost N events.

Aggregate in the kernel, filter early, size the buffer, and count your drops.

Two practical questions from SREs: what does this cost, and can I trust the numbers? The kernel can count runs and nanoseconds per program once you enable bpf_stats; overhead.sh in the examples does this and prints the average. In the sandbox run a simple counting program cost about 130 nanoseconds per syscall. Multiply by the event rate to get the CPU cost. The second point: BPF never blocks the traced process. If user space does not read fast enough, events are dropped. The Go example in 10-overhead-drops makes this visible by reading slowly and counting failed reservations. Tools that stream every event must report drops, and you should look at them before trusting a latency percentile.
