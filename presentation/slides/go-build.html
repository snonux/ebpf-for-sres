Building it

mage, go:embed and a static binary

$ cd examples/01-opens-per-process
$ mage            // build
  clone libbpfgo v0.9.2-libbpf-1.5.1  (once)
  make libbpfgo-static → libbpf.a     (once)
  bpftool btf dump … > vmlinux.h      (once)
  clang -target bpf -c opens.bpf.c
  go build   // opens.bpf.o embedded
$ sudo ./opens -duration 5s
$ sudo -E mage test   // run under load, check output
$ mage static         // fully static binary

magefile.go per example

Five lines each, all calling one shared helper: internal/magebpf. The same steps ior uses, nothing more.

Static, for real

mage static needs libelf.a and libzstd.a, which Rocky 9 does not ship: Containerfile.static builds them, as ior does.

CO-RE + static =

one 5 MB file with the BPF object inside. Copy it to a host or into a container and run it.

How the Go examples are built, which is the boring part that usually takes the longest to get right. Each example directory has a magefile with build, static, test and clean targets, and they all call one shared helper. The first build clones libbpfgo at the version ior uses, builds a static libbpf from it, and dumps vmlinux.h from the kernel's BTF. Then clang compiles the BPF C, and go build embeds the object. For a fully static binary you need static libelf and zstd, which Rocky does not package, so there is a Containerfile that builds them. The payoff of CO-RE plus static linking is one file you can copy anywhere, which we need for Kubernetes in a moment.
