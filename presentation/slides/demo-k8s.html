The debug-container workflow, rehearsed with podman

$ sudo podman run -d --name app --mount type=tmpfs,destination=/store \
      registry.access.redhat.com/ubi9/ubi-minimal \
      sh -c 'while true; do dd if=/dev/zero of=/store/data bs=4k count=64 conv=fsync; done'
$ sudo podman run -d --name debug --privileged --pid=container:app \  // like kubectl debug --target
      docker.io/library/busybox sleep 3600          // runs as root
$ sudo podman cp storeiops debug:/tmp/storeiops              // the static binary, built before the talk
$ sudo podman exec debug ps                                  // PID 1 is the app
$ sudo podman exec debug /tmp/storeiops -pid 1 -path /store -bycomm -duration 15s

With a cluster at hand, run the four kubectl commands from the workflow slide instead. Show the code from the previous two slides in the editor if there is time.

Second demo, about five minutes. Build the static binary before the talk. These five podman commands reproduce the Kubernetes setup on one Rocky box, typed out so nothing is hidden: an app container writing to a /store volume, a privileged debug container in the app's PID namespace, a podman cp of the binary, and then storeiops tracing PID 1. Point out that nothing from the host or from other containers shows up, only I/O on /store. The repository's podman-demo.sh runs the same five commands, for rehearsal. If you have a cluster, do the real kubectl version instead.
