storeiops, user side

From "PID 1, /store" to two numbers

func target() (mntns uint64, dev uint32) {
  var st syscall.Stat_t
  // the app's mount namespace
  syscall.Stat("/proc/1/ns/mnt", &st)
  mntns = st.Ino
  // the app's /store, seen from the debug container
  syscall.Stat("/proc/1/root/store", &st)
  dev = kernelDev(st.Dev)  // user ≠ kernel encoding
  return
}

m, _ := bpfrun.Load(bpfObj, "storeiops.bpf.o",
  func(m *bpf.Module) error {
    m.InitGlobalVariable("target_mntns", mntns)
    return m.InitGlobalVariable("target_dev", dev)
  })                                // then load + attach
for now := range tick {             // every second
  report(now, m.GetMap("stats"))    // read + delete
}

/proc does the work

Sharing the PID namespace gives us /proc/1: its ns/mnt identifies the container, its root/ is the app's file system.

Set before load

Globals are written into the object before the verifier sees it. That is how ior sets its PID filter.

Container gotcha

No tracefs in the debug container: storeiops mounts it before attaching.

The user side is mostly plumbing, and the interesting part is how little it needs. Because the debug container shares the app's PID namespace, /proc/1 is the app: stat of its ns/mnt link gives the namespace inode, and stat of /proc/1/root/store gives the device of the app's /store mount, even though the debug container has no such mount itself. The device number has a different encoding in user space and in the kernel, so it is converted. Both values go into the BPF object as globals before loading, the same trick ior uses for its PID filter. Then every second we read and clear the stats map and print it. One real gotcha we hit: containers do not have tracefs mounted, and libbpf needs it to attach tracepoints, so the tool mounts it.
