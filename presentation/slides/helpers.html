Some helpers change things

bpf_skb_store_bytes()
bpf_redirect()		Rewrite or redirect network packets. Load balancers and Cilium are built on this.
bpf_override_return()Make a kernel function return an error without running it. For fault injection.

Not in this talk

A wrong packet rule or an injected error can take a service down, even though the verifier accepted the program.

Everything we build today only observes: it reads, counts and reports. It changes nothing on the system.

A BPF program cannot call arbitrary kernel functions. It can only call helpers, a fixed list the kernel exposes, and each program type gets its own subset. On the left are the ones our examples use, and they only observe: who is running, its name, a timestamp for latencies, our own maps, a safe copy of a string such as a file name, and the ring buffer to send an event to user space. BPF_CORE_READ, which we meet later, is in the same family. But BPF is not read-only by nature. Networking programs rewrite and redirect packets; that is how load balancers and Cilium work. bpf_override_return makes a kernel function return an error without running it, for fault injection, and only on functions the kernel marks as safe for that. bpf_probe_write_user writes into a process's memory; the man page itself warns of a risk of crashing the system and running programs, and the kernel logs a warning when such a program is attached. A program can never write arbitrary kernel memory, but with these helpers a verified program can still break a service: drop the wrong packets, fail the wrong call. So keep the two worlds apart in your head. Everything in this talk observes only: it reads, counts and reports, and that is why it is comfortable to run on production.
