CO-RE needs BTF

The kernel describes its own types

BTF = BPF Type Format

Compact type metadata: every struct, field, offset and function signature of the running kernel. Built from debug info at kernel build time (CONFIG_DEBUG_INFO_BTF=y).

Where it lives

/sys/kernel/btf/vmlinux, on by default in Rocky and RHEL 9 (since 8.2). Our sandbox: 5.5 MB, 126,611 types. No kernel-devel, no debuginfo.

Who reads it

libbpf at load time to patch field offsets (CO-RE); bpftrace for curtask->… and args; bpftool to generate vmlinux.h.

Ask the kernel where a field is

$ bpftool btf dump file /sys/kernel/btf/vmlinux \
    | grep -A250 "STRUCT 'task_struct'"
[114] STRUCT 'task_struct' size=3264 vlen=248
  ...                             // trimmed to 3 of 248 fields
  'pid'  type_id=68 bits_offset=10112
  'tgid' type_id=68 bits_offset=10144
  'real_parent' type_id=115 bits_offset=10240

10240 bits = byte 1280: the offset libbpf patches in on this kernel.

One header for every kernel type, built once

$ bpftool btf dump file /sys/kernel/btf/vmlinux \
    format c > vmlinux.h     // 134,773 lines
#include "vmlinux.h"          // in foo.bpf.c

CO-RE only works because the kernel carries a description of itself. That description is BTF, the BPF Type Format: a compact encoding of every type in the kernel, so every struct, every field with its offset, and every function signature. It is produced from the debug info when the kernel is built and exposed at /sys/kernel/btf/vmlinux. Rocky and RHEL 9 ship it on by default, so you need neither kernel-devel nor debuginfo packages. On our sandbox kernel it is 5.5 MB and describes about 126,000 types. You can read it yourself with bpftool: here task_struct, and real_parent at bit offset 10240, which is byte 1280, exactly the number libbpf will patch into our program on this kernel. The same command with format c writes vmlinux.h, one header with every kernel type, which our BPF C files include instead of kernel headers. bpftrace reads the same file when you write curtask->real_parent.
