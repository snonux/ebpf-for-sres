Needs a toolchain on every host

bpftrace links LLVM and Clang: ≈250 MB of libraries on Rocky 9.9, ≈160 MB of memory per run.

Slow when it matters

In an incident you first install packages, then compile, on the box that is already in trouble. Minimal and distroless containers have no package manager at all.

A compiler in production

More packages to patch, and a compiler plus root is exactly what an attacker hopes to find. Many hardening baselines forbid it.

What we want instead: one binary, built and tested ahead of time, that runs on every host. Copy it, run it.

bpftrace is the easy part, and here is the catch that shapes the rest of the talk. bpftrace is a complete compiler: it parses the script, resolves types from the running kernel, and then LLVM compiles it to BPF, on the host you are tracing, every time you start a script. You just saw that scroll by with -d all. Three consequences. First, every host needs the toolchain: on Rocky 9.9 bpftrace pulls in about 250 MB of LLVM and Clang libraries, and the one-liner peaks at about 160 MB of memory. Second, speed: in an incident you do not want to start by installing packages and compiling on the box that is in trouble, and in a distroless container you cannot. Third, security: a compiler on a production host is more to patch and a gift to an attacker, and many hardening baselines forbid it. bpftrace stays the right tool for exploring on a box where it is already installed. But for anything you want ready before the incident, we want a binary that is built and tested ahead of time and simply runs everywhere. The next slides are about what stands in the way of that, and how CO-RE removes it.
