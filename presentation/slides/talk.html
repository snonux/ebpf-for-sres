Maps for totals, the ring buffer for single events, globals for settings. Every bpftrace @variable is a map.

Example 11 used one way to get data out: a map. There are three channels, and this is the picture. Every BPF tool is two programs that never call each other. The kernel half runs on every event; the user half runs whenever it likes. They meet in the middle, in kernel memory that both sides can reach. Top row: the BPF side bumps a counter in a hash or array map, and user space reads the totals every few seconds or at the end. This is the cheapest channel because only the summary crosses. Middle row: for individual events the BPF side writes a record into a ring buffer and user space receives it, here on a Go channel; that costs more and can drop events when the reader is slow. Bottom row goes the other way: user space sets global variables like a target PID before loading, and the verifier treats them as constants, so the filter costs next to nothing. User space reaches all of this through the bpf() syscall and file descriptors; the ring buffer is even memory-mapped, so events are not copied. A few more details: per-CPU maps give lock-free counters on hot paths, the perf buffer is the older per-CPU event stream from before kernel 5.8, and maps can be pinned in /sys/fs/bpf to outlive the loader. And every bpftrace @variable is simply a map.
