Example 06: kprobes

Hook any kernel function, at a price

kprobe:vfs_read    { @start[tid] = nsecs; }
kretprobe:vfs_read /@start[tid]/ {
    @usecs = hist((nsecs - @start[tid]) / 1000);
    delete(@start[tid]);
}

SEC("kprobe/vfs_read")    int BPF_KPROBE(enter)
SEC("kretprobe/vfs_read") int BPF_KRETPROBE(exit)

Power

Any of ~50,000 kernel functions, not only the ones with a tracepoint. Sees reads from every path into the VFS, not only read().

Price

vfs_read is an internal function: it can be renamed, inlined or change arguments in the next kernel. Your probe then fails to attach.

examples/06-vfs-read-latency-kprobe/ · vfsreadlat.bt · vfsreadlat.stp · Go

Same latency pattern as example 05, but on a kernel function instead of a syscall tracepoint. kprobes can go almost anywhere, which is their power, and they are tied to one kernel build, which is their price. On Rocky 9 vfs_read is a stable, non-inlined function, so this example works, but it is exactly the kind of probe that breaks on an upgrade. The C version uses the BPF_KPROBE macros from libbpf, which hide the register access. In the sandbox this one could not run because that kernel has no kprobe support at all, which is a nice reminder to check before an incident.
