Everything so far was the kernel. uprobes do the same for user space: put a probe on any function in a binary or shared library, with no code change and no restart. For compiled languages, C, C++, Rust and Go, that works on any function symbol, as long as the binary is not stripped. One trap with Go: do not use uretprobes. The return probe rewrites the return address on the stack, and when Go grows and moves a goroutine stack the runtime finds that address and kills the process with unknown caller pc; the Go issue for it has been open since 2017. Put uprobes on the function's RET instructions instead. Shared libraries are the sweet spot: one probe on getaddrinfo in libc covers every program, that is example 07, and a probe on SSL_write in OpenSSL shows data before it is encrypted. For JIT-compiled and interpreted languages a uprobe has nothing stable to attach to, because the code is generated at run time. So the runtimes ship USDT probes, static markers compiled in, the same ones DTrace uses. HotSpot has probes for GC, class loading, threads and compilation; method entry needs -XX:+DTraceMethodProbes and object allocation -XX:+DTraceAllocProbes, and both are slow. Up to JDK 19 one flag, ExtendedDTraceProbes, switched them all on; JDK 20 removed it. CPython has function entry and return and GC markers if it was built with --with-dtrace; check with readelf -n for stapsdt notes. bpftrace -l lists what a binary offers. Remember the cost: each uprobe hit is a trap into the kernel, microseconds, so not on malloc.
