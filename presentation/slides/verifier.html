The VM and the verifier

What the kernel checks, and what it cannot

Checked before it runs

A small VM

11 registers, a 512-byte stack, a fixed instruction set, JIT-compiled to native code.

Every path

The verifier walks all branches. Loops must be bounded (5.3+). Up to 1M instructions are analysed, then "too complex".

Every access

Pointers are range-checked; a map lookup must be NULL-checked; user memory only via helpers.

Allowed calls

Only BPF helpers and kfuncs, no arbitrary kernel functions. Locks must be released.

Not its job

CPU cost

A 100 ns program on an event firing 1M times/s costs a CPU core.

Memory

Maps are kernel memory: max_entries × value size, times CPUs for per-CPU maps.

Contention

A shared counter or bpf_spin_lock hit from 64 CPUs serialises them. Use per-CPU maps.

The verifier is what makes BPF safe enough for production, so it is worth knowing what it does. It simulates the program on every path, which is why loops must be bounded and why big programs fail with a complexity error. It checks every memory access and forces you to handle a failed map lookup. What it proves is that your program cannot crash the kernel or hang it. It does not stop a correct program from being expensive: attaching to a very hot event, allocating a map with millions of entries, or making all CPUs fight over one lock or one shared counter is all allowed. Those are the ways BPF tools hurt production boxes in practice.
