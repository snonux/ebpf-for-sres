The force multiplier

BPF + SRE + LLM == Superpowers

Write

"IOPS per process on /store, only for this pod" becomes a .bpf.c and a Go loader in minutes. Paste verifier errors back and it fixes them.

Build

The fiddly glue: the build, the static binary, the Containerfile. Every example in this repo was built and tested this way.

Analyse

Give it the trace and the app's source code: it maps syscall patterns, like an fsync after every record, to the lines that cause them.

Still your job

Run it on staging first and read what it wrote. The verifier proves the program is safe, not that the numbers are right.

BPF gives you the facts, the LLM gives you the code and the explanation, the SRE decides.

This is the slide that ties it together. BPF used to have a steep learning curve: the verifier, CO-RE, the build and deployment glue. LLMs flatten it. They write the BPF C and the loader from a plain description, they know the verifier's rules and fix its error messages, and they handle the build plumbing that usually eats the afternoon. All examples in this repository were written that way and then tested on a real kernel, including finding the RHEL 9 tracepoint quirk. And on the analysis side, an LLM that gets both a syscall trace and the source code can tell you which code path produces the pattern you see. The caveat is the usual one: you stay responsible for what runs on production.
